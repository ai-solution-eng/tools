## 2. Changes made for PCAI

### 2.1 The `ezua` block (values.yaml)

| Key | Value | Why |
|---|---|---|
| `ezua.enabled` | `true` | gates the VirtualService |
| `ezua.domainName` | `${DOMAIN_NAME}` | PCAI substitutes it at import time; kept verbatim |
| `ezua.virtualService.endpoint` | `mooncake.${DOMAIN_NAME}` | the public dashboard host; must be unique on the shared gateway |
| `ezua.virtualService.istioGateway` | `istio-system/ezaf-gateway` | the platform gateway, fixed |
| `ezua.virtualService.timeout` | `30s` | dashboard reads are short |
| `ezua.authorizationPolicy.*` | `enabled: false` | the template ships but is off by default — the dashboard is read-only. Flip to `true` to put SSO in front of it |

### 2.2 VirtualService

`templates/virtualservice.yaml` routes the gateway host to the **dashboard** service
(`<release>-ui.<namespace>.svc.cluster.local:<ui.service.port>`, default 8080) — the UI is
the only thing a human needs to reach. The master stays cluster-internal (clients use it
in-cluster; operators use `kubectl port-forward`).

### 2.3 AuthorizationPolicy

The template exists and is wired to `ezua.authorizationPolicy.enabled`; it is **disabled**
in the shipped values. Rationale: the dashboard exposes pool statistics only, and the
import flow should not depend on an oauth2-proxy provider being present. Enable it if the
stats must not be readable by every in-cluster caller.

### 2.4 `hpe-ezua` labels

Applied **natively** in every template (no Kyverno): every Deployment, StatefulSet,
Service, ConfigMap, Role/RoleBinding and ServiceAccount carries
`hpe-ezua/type: vendor-service` and `hpe-ezua/app: {{ .Chart.Name }}`, and the pod
templates carry them too so the labels reach the pods.

### 2.5 Storage: a PVC per store pod

The pool is a **StatefulSet**, not a Deployment, and its capacity tier is a
**`volumeClaimTemplates` PVC per pod**:

- `templates/statefulset-store.yaml` — one DRAM segment (`store.segmentSize`) **and** one
  PVC (`store.persistence.size`) per pod. The claim template means the volume follows the
  pod across restarts and reschedules, which is what makes the capacity tier durable.
- `templates/service-store-headless.yaml` — the StatefulSet's stable per-pod DNS. Clients
  do not use it; they dial the address each store pod registers with the master.
- SSD offload is switched on by the presence of the PVC: with `store.persistence.enabled`
  the store pod's args carry `-Denable_ssd_offload=true` and
  `-Dssd_offload_path=<mountPath>`. The `-D` overrides are the only supported way to set
  them — the SGLang-style `MOONCAKE_*` env names do nothing for this service.

**Why the DRAM segment was not removed.** `MOONCAKE_GLOBAL_SEGMENT_SIZE` is registered
host **memory**, not disk: the store serves KV pages out of it. A PVC cannot replace it —
a pod with no segment has nowhere to put a page. The PVC is the capacity tier *behind*
the DRAM hot cache, so the two are sized separately and both appear in values.

### 2.6 Other PCAI-driven choices

- **No custom image for the dashboard.** The app is a single stdlib-only `app.py` shipped
  in `files/app.py` and mounted from a ConfigMap into the stock `python:3.14-slim` image
  (the same base image as the fleet's other apps; the app is stdlib-only and was
  verified on 3.14).
  This keeps the chart importable on a unit with no registry access, and it means the
  dashboard can be updated with `helm upgrade` instead of an image build.
- **RBAC is per discovery namespace.** The chart creates a read-only Role + RoleBinding
  (`get`/`list` on pods **and on persistentvolumeclaims**) in the release namespace and in
  every namespace listed in `ui.discovery.namespaces` — the dashboard lists pods to find
  Mooncake clients, and reads the PVC claims as the honest denominator for the disk tier
  (the master's self-reported pool figure does not match the claims it sits on).
  `ui.rbac.create: false` disables creation; `ui.serviceAccount` names the bound account.
- **No CRDs, no HPA, no operators.** Three workloads, three services, one VirtualService.
- **Site overlays live outside the package.** `values-examples/` and `local/` are excluded
  by `.helmignore`, so a site file with real storage-class names never ships in the tgz.

## 3. Verification

```
$ helm lint helm
==> Linting helm
[INFO] Chart.yaml: icon is recommended
1 chart(s) linted, 0 chart(s) failed

$ helm template mooncake helm -n mooncake \
      --set ezua.virtualService.endpoint=mooncake.example.com
```

Rendered objects (defaults): ServiceAccount `mooncake-ui`, ConfigMap `mooncake-ui`,
Role + RoleBinding `mooncake-ui-reader`, Service `mooncake-master`, Service
`mooncake-store-headless`, Service `mooncake-ui`, Deployment `mooncake-master`,
Deployment `mooncake-ui`, StatefulSet `mooncake-store` (with `volumeClaimTemplates`),
VirtualService `mooncake-vs`. The AuthorizationPolicy is absent while disabled — by design.

> Gotcha found during the port: a `.helmignore` containing a `!negation` pattern made
> Helm 4.3 report `Chart.yaml file is missing` for an otherwise valid chart. The shipped
> `.helmignore` therefore uses plain patterns only.

## 4. Deploying on PCAI

1. `helm package ./helm` → `helm/mooncake-0.2.0.tgz`.
2. In PCAI: **AI Essentials → Tools & Frameworks → Import Framework**, upload the `.tgz`,
   review the values, and install into a new namespace (`mooncake` suggested).
3. Values most likely to be changed: `ezua.virtualService.endpoint` (must be unique),
   `store.persistence.storageClassName` (on G2 today, `gl4f-filesystem`; swap for the X10000 class when one exists), `store.replicaCount` and
   `store.persistence.size` (pool size), `ui.discovery.namespaces` (where your model
   deployments live).
4. The app appears at `https://mooncake.<cluster-domain>` once the VirtualService is
   programmed, and in the PCAI UI under Tools & Frameworks.

Alternative (no UI): `helm install mooncake ./helm -n mooncake --create-namespace \
-f helm/values-examples/values.g2.yaml`.
