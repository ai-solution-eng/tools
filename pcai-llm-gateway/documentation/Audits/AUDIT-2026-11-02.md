## 1. P1 — five, ALL FIXED

### P1-1 Admission failover promoted the MODEL but not the POOL — FIXED
**Defect.** routes_proxy.py resolved the pool at :3551 **before** the admission walk. That walk returns a possibly different model by design (a rate/budget 429 fails over down the ordering), and the pick at :3849 still used the stale pool — so the request went to the **exhausted model's endpoint** carrying the **promoted model's name** in the body.

**Impact.** A strict vLLM/SGLang turns the documented 429-failover into a 400/404. A permissive upstream **serves the model whose per-model budget gate just refused** while the ledger books it against another model — a per-model budget bypass (thesis clause 4), invisible because the ledger is internally consistent.

**Fix.** Pool re-resolved after the walk, inside the slot-releasing try; candidates filtered to chat pools (the resolution order carries embedding pools).

**Pin.** A route-level test asserting **which upstream HOST** the failover reached. That assertion did not exist before — precisely why the bug survived a green suite.

### P1-2 A derived team envelope did not bound the team's TOTAL spend — FIXED
**Defect.** budgets.py consulted only the caps naming the request's model, and skipped the pooled check whenever tokens was in team.derived_dims — which is *every* derived team. The pooled number the console displayed was a parallel bound only unnamed models ever faced.

**Impact.** Real ceiling ~2x the displayed cap. Reproduced: team total at 2.5x the envelope still admitted, with **zero pooled queries issued**. Violates thesis clauses 4 and 5.

**Fix.** Both derived_dims guards dropped; the pooled total binds after the per-model caps. The one-round-trip property was then restored by folding the ('*', period) scope into the same team_cap_spend call instead of issuing a second aggregate.

**Pin.** Pooled refusal + exactly one cap-spend round trip + no separate spend call.

### P1-3 Stored XSS in the admin console via a team-leader-chosen key name — FIXED
**Defect.** admin.html interpolated the key name **unescaped** into banner(), which is raw innerHTML. The identical banner in team_leader.html escaped it. The backend accepted any 200-char name with **no charset validation**.

**Impact.** A team leader (delegated, non-admin) mints a key whose name is an img tag with an onerror handler; an admin saves that key's edit; the payload fires in the console holding the **fleet admin bearer in sessionStorage**, with CSP script-src 'unsafe-inline' as no backstop. Reproduced in a DOM harness with the verbatim page functions: LIVE ELEMENT INJECTED.

**Fix.** banner() escapes by default with an explicit HTML opt-in. **Correction to the Lead's instruction:** I said one site needed markup; a mechanical sweep found **18**, all now opted in, and **69** pre-escaped sites were un-escaped to avoid double-escaping under the new contract.

**Defence in depth (found during remediation, not in the audit).** The charset rule now covers all **three** doors — admin KeyCreate/KeyPatch, team-leader TeamKeyMint/TeamKeyPatch, and the **public unauthenticated enroll door** (EnrollRequest.name), which the audit missed and which was the most reachable way to put markup into the column the admin console renders. One definition in routes_admin, imported by both other modules; the false "a cycle forbids the import" comment that caused the duplicate is gone.

**Pins.** Hostile key name renders inert (behavioural, verbatim page functions under node); 422 on all three doors with a positive unicode control; the enroll pin also proves the code is NOT burned on refusal.

### P1-4 The SSO self-mint kill switch was enforced by the probe but never by the mint — FIXED
**Defect.** settings.sso_key_create_enabled (default **False**) existed at exactly two places: its definition and the /v1/identity probe. Neither for-me handler read it. With the flag False the probe returned self_mint: false while the mint returned **201 with a live key** — no budgets at all when no tenant default profile is wired.

**Impact.** An operator who freezes key issuance via the documented flag during an incident does not freeze it, while the console and the probe both say they did. Silent absence of a security control. **Lead severity correction: P2 -> P1.**

**Fix.** Conjunct added to BOTH handlers, placed before the subject lookup so the anti-oracle contract holds (byte-identical refusal detail for "off" and "not eligible").

**Pin.** Flag-off 403 on both, byte-identical bodies, no key/user row written. The existing fixture ran with the flag False and **pinned the bug** — it now states the enabled posture explicitly; no assertion was weakened or inverted.

### P1-5 The delegated team-leader mint ignored the enrollment's mint allowance — FIXED
**Defect.** POST /team_leader/keys never read max_uses and never incremented uses, while the redeem door enforced the same ceiling atomically (UPDATE ... AND (uses < max_uses)).

**Impact.** Reproduced: 3x 201 from a max_uses=1 enrollment, with the admin's uses counter staying at 0. The delegated non-admin console was the product's only unbounded mint surface; it decoupled the derived envelope's N from the real seat count. Found **independently by two model families** (GLM admin-identity F2, DeepSeek teams-leader #2). **Lead severity correction: P2 -> P1.**

**Fix.** The redeem door's conditional UPDATE is now the FIRST statement in the mint transaction; a refusal raises 409 and rolls back so a refused mint consumes no seat.

**Pin.** 2nd mint 409, uses stays 1, no INSERT INTO api_keys.

**This is the phase's payoff:** the suite was green when wave 1 found that GAP. Green tests are evidence of coverage, not of correctness.

## 9. Added on owner request

### 9a. Postgres pool observability

`core/metrics.py` now exports three gauges, registered only when prometheus_client is
present (the module's existing import guard) and read at SCRAPE time:

| Metric | Meaning |
|---|---|
| `gateway_db_pool_size` | connections currently open in this process's pool |
| `gateway_db_pool_idle` | open but unused |
| `gateway_db_pool_max` | the configured ceiling (`dbPoolMax`) |

**Why scrape-time functions rather than a background updater:** the pool handle is
replaced on reconnect, so a value captured at import would go stale or point at a
closed pool. `Gauge.set_function` re-reads `db.pool` on every scrape, and the lazy
import keeps `core.metrics` importable without `db/` (which imports it).

**Reading it.** The aggregate is `sum()` across pods, and that is the number that must
stay under the server's `max_connections`:

```promql
sum(gateway_db_pool_size)                                  # aggregate demand right now
sum(gateway_db_pool_max)                                   # worst case if every pod saturates
max(gateway_db_pool_size) by (pod)                         # which pod is hot
max_over_time(gateway_db_pool_size[1h])                    # peak demand (the sizing number)
```

**How to decide whether to raise `dbPoolMax`:** `size` sustained at `max` with `idle`
near 0 means the pool is the constraint; `size` well under `max` means raising it buys
nothing. A pool that is genuinely starved also shows up as `db_acquire_timeout_s` (2 s)
failures, which are logged.

Pins: values rendered from a fake pool; zeros with no pool; zeros (not an exception)
when the pool's stat methods raise — a metrics scrape must never fail the request path.
All three are structurally pre-fix failures: the metric names do not exist in HEAD.
